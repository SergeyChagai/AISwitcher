# ADR-0004: Стек реализации — Rust

## Status

Accepted

## Context

[ADR-0001](./ADR-0001-two-tier-detection-pipeline.md) и
[ADR-0003](./ADR-0003-windows-input-interception.md) задают требования, которые в сумме
определяют выбор языка сильнее, чем привычки команды.

**Требование, определяющее всё остальное:** обработчик низкоуровневого клавиатурного хука
синхронен и разделяем на всю систему. Задержка внутри него — это задержка ввода во всех
приложениях сразу, а при превышении системного таймаута Windows молча снимает хук, и продукт
тихо перестаёт работать. Значит, на этом пути недопустимы паузы, которых автор кода не
контролирует.

Это прямой аргумент против управляемых сред: пауза сборщика мусора в потоке хука подвешивает
ввод во всей системе. Дизайн «хук только кладёт событие в очередь» (ADR-0003) сильно снижает
вероятность, но не устраняет её как класс — поток всё равно принадлежит рантайму с GC.

Остальные требования:

- Фоновый процесс, который пользователь не запускал осознанно: RAM в десятках мегабайт, CPU в
  покое около нуля.
- Tier 1 требует инференса ONNX-модели, если ADR-0002 закончится в её пользу.
- Глобальный хук вызывает реакцию антивирусов, поэтому нужен предсказуемый, подписываемый
  бинарник без тяжёлого рантайма в комплекте.

Контекст владельца проекта: основная платформа — C#, но низкоуровневый Windows-опыт есть
(`clumsy`, C + WinDivert).

## Decision

Реализация на **Rust**.

- **Windows API** — через `windows` (windows-rs): хук, определение и переключение раскладки
  активного окна, `SendInput`.
- **Инференс Tier 1** — через `ort` (обёртка над ONNX Runtime), если ADR-0002 выберет
  ONNX-модель. Крейт подключается только вместе с решением по ADR-0002 — до этого зависимости
  на инференс в проекте нет.
- **Трей** — `tray-icon`.
- **Tier 0** пишется без внешних зависимостей: карта раскладок и n-граммный скорер — это
  таблицы и арифметика.

Ключевое следствие для кода: отсутствие GC означает, что путь хука имеет предсказуемую верхнюю
границу времени, и её можно доказать, а не надеяться на неё. Требование «хук только кладёт в
очередь» из ADR-0003 остаётся в силе — оно про архитектуру, а не про язык.

## Consequences

- Латентность горячего пути определяется написанным кодом, без вклада рантайма. Это то
  свойство, ради которого выбор сделан.
- Единый статически слинкованный бинарник без предустановки рантайма — проще подписывать и
  проще объяснять антивирусу.
- Плата: Rust не является основной платформой владельца проекта. Скорость разработки на первых
  спринтах будет ниже, чем на C#.
- Плата: экосистема desktop-UI в Rust беднее. Для трея и настроек этого достаточно, но если
  продукту понадобится содержательный UI, решение придётся пересматривать отдельным ADR.
- `unsafe` неизбежен на границе с Win32. Он должен быть локализован в тонком слое обёрток над
  API, а не расползаться по логике.

## Alternatives Considered

- **C# / .NET 8 NativeAOT.** Основная платформа владельца, первоклассный
  `Microsoft.ML.OnnxRuntime`, трей из коробки, самая высокая скорость разработки. Отвергнут
  из-за GC в пути хука: NativeAOT убирает стартовый оверхед и JIT, но не сборщик мусора.
  Остаётся кандидатом, если Rust окажется неоправданно дорогим по времени — тогда потребуется
  новый ADR, заменяющий этот.
- **C++.** Даёт тот же контроль над горячим путём и родной API ONNX Runtime, но требует ручной
  работы на всё остальное — сборку, зависимости, трей, конфиг — без выигрыша по существу
  относительно Rust.
- **Гибрид: нативная DLL для хука + C# для логики и UI.** Снимает вопрос GC полностью и
  сохраняет привычную платформу для основной части. Отвергнут из-за цены: граница interop,
  две системы сборки и две цели подписи ради проекта, который целиком помещается в один
  бинарник.
- **Electron / Node.** Отвергнут безусловно: сотни мегабайт RAM для фонового процесса
  противоречат самому смыслу продукта.

## Open Questions

- Один процесс или разделение на процесс хука и процесс детекции? Разделение изолирует падение
  логики от ввода пользователя, но добавляет IPC.
- Способ подписи бинарника и его стоимость.
- Нужен ли UI-фреймворк для окна настроек, или хватит трея и конфиг-файла.
